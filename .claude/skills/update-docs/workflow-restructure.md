# Workflow: restructure docs

Example: `/update-docs restructure docs with tabs like ...`

Restructuring changes URLs and navigation. Plan everything and get approval before you move anything.

## 1. Understand the request

Typical kinds:
- **Tabs inside a page**: show alternatives side by side (e.g. "Using Gupshup" vs "Using Meta Cloud API", or "Web" vs "Mobile").
- **Merge/split pages**: combine thin pages, or split a long page into a folder.
- **Move/reorder**: change the section or the order in the sidebar.

If the request is vague ("restructure with tabs like …"), ask for, or propose, one concrete before/after example first.

## 2. Map the current structure

- The sidebar is autogenerated from `docs/` (`sidebars.js`). Order comes from numeric filename prefixes and `_category_.json` (`position`, `label`).
- List the affected files, their URLs (the path under `docs/` without the number prefixes; check the page frontmatter for `slug`/`id`) and inbound links: `grep -rn "<filename or path fragment>" docs src`.

## 3. Plan → confirm

```
Restructure plan:
- docs/a.md + docs/b.md → docs/x/01. A.md (tabs: "Gupshup" | "Meta")
- moved: docs/old/path.md → docs/new/path.md   (URL changes: /old/path → /new/path)
- inbound links to update: N files
- _category_.json changes: ...
- redirects: none available (no redirect plugin) — URL changes will 404 for external links
```

Point out every URL change. Wait for approval.

## 4. Apply

Tabs syntax (pages are MDX, so imports work in `.md`):

```mdx
import Tabs from '@theme/Tabs';
import TabItem from '@theme/TabItem';

<Tabs groupId="bsp">
  <TabItem value="gupshup" label="Gupshup" default>

  Steps for Gupshup…

  ![Gupshup settings](/img/settings/settings_gupshup.png)

  </TabItem>
  <TabItem value="meta" label="Meta Cloud API">

  Steps for Meta…

  </TabItem>
</Tabs>
```

- Leave a blank line after `<TabItem …>` and before `</TabItem>` so the markdown inside renders.
- Use the same `groupId` on related pages so the reader's choice carries over.
- Put the imports after the frontmatter and before the header block.
- Use `git mv` for moves so history is kept. Update `_category_.json` where needed.
- Update every inbound link that you found.
- If the new layout needs new screenshots (e.g. one per tab), take them with `gdocs shot`.

## 5. Validate

- `gdocs lint $(git ls-files 'docs/*.md' 'docs/**/*.md')`: this checks every page, including unchanged pages that link to moved files. Ignore failures that `main` already has; fix any that mention the paths you moved.
- `grep -rn "<old path fragments>" docs src` must return nothing.
- `gdocs lint` checks relative `.md` links in changed pages. `onBrokenLinks` is `ignore` in `docusaurus.config.js`, so the build won't catch broken links.
- Run `yarn build` if `node_modules/` exists, to catch MDX errors such as unclosed `<TabItem>`. Otherwise say that CI will check it.
- In the summary, list every URL that changed.
